# 《此生为蛇》设计意图 GDD

> 本文件只定义产品幻想、体验目标、设计关系和长期边界，不镜像当前运行时数值、源码实现或项目进度。运行时事实以当前代码与 `snake55/02_config.js` 为准；当前完成度与开放问题以 `docs/STATUS.md` 为准；工程权限以 `AGENTS.md` 为准。

## 1. 定位与核心幻想

《此生为蛇》是一款原生 JavaScript + Canvas 的单人网页 Roguelike 生存游戏。玩家操控一条持续前进的蛇，在敌潮和资源之间作出取舍，通过吞噬、成长、自动技能与 Combo 形成一套越来越有个性的战斗构筑，并在死亡或完成一局后把这段经历转化为“蛇生”结算。

核心幻想是：一条蛇越贪越强，也越容易把唯一的命门置于危险之中。玩家不是被动等待数值增长，而是在“再吃一口、再撑一波、再靠近一点”和“现在撤开、保住这条命”之间主动写下这一生。

## 2. 设计柱石与张力

### 2.1 蛇身即身份

蛇不是普通角色的贴图。蛇身同时承担移动轨迹、成长记录、技能承载、战斗轮廓和记忆载体。蛇头是玩家最需要保护的行动焦点；蛇身的长度和状态应让玩家感到“这条蛇正在成为它自己”。

### 2.2 贪婪悖论

资源、战斗收益和更强构筑会诱导玩家靠近危险。贪婪必须是玩家可理解、可归因的选择，而不是由不可读的随机伤害强迫产生。玩家应能回看一次死亡并说清楚：我为了什么收益把蛇头放进了那个位置。

### 2.3 爽与静

战斗阶段提供连续的操控、清理、成长和力量反馈；结算阶段把喧闹收束为停顿、回忆和重新开始。两种情绪不是互相覆盖的装饰，而是同一段蛇生的前后两面。

### 2.4 设计边界

- 先保证可读、可操作、可归因，再追求更密集的表现。
- 手感是入场券：操控、反馈和节奏必须先让玩家愿意继续玩，再承载更复杂的内容。
- 视觉、音频和文字服务于战斗信息、身份识别与情绪节奏，不另起一套 gameplay 真相。
- 强构筑应带来力量反差，但不能靠不可读的威胁或单纯堆血制造挑战。
- 每个新增系统都要回答：它给玩家增加了什么新的选择、风险或操作题？

## 3. 双层循环

### 3.1 战斗循环

玩家控制蛇头寻找路线，吞噬资源获得成长，选择或强化技能，利用蛇身展开自动战斗能力，在敌潮中寻找安全与收益的平衡。敌人、资源、技能和场景共同把玩家推入“接近危险—处理威胁—取得收益—重新选择”的短循环。

### 3.2 Session 循环

一局由准备、探索、构筑、战斗、面对终点威胁和结算组成。死亡不是单纯失败画面，而是把本局的选择、击杀、受伤、成长和关键时刻整理成可回味的蛇生记录；完成一局则提供另一种收束。结算应促使玩家想要重开，尝试不同构筑或更谨慎的路线。

## 4. 操控、生存与蛇的身体

- 蛇持续向当前方向前进，输入主要表达转向意图；松手后仍保持可预测的运动。
- 玩家应能用方向、距离和路线管理危险，而不是依靠瞬时反应猜测碰撞。
- 蛇头承担主要生存风险，蛇身的存在感来自空间占据、技能覆盖和成长反馈；任何例外都必须有清晰的设计理由与专门验收。
- 自身移动、碰撞、伤害、无敌、掉落与表现层保持职责分离。GDD只描述体验契约，不规定实现细节。

## 5. 成长、构筑与 Combo

### 5.1 成长

吞噬应同时让玩家感到身体变长、战斗能力变强和蛇生记录变丰富。成长不是孤立的经验条，而是把资源选择、空间风险和后续构筑串起来的反馈。

### 5.2 构筑

技能通过选择形成构筑方向。技能可以沿蛇身、围绕蛇体或在战场空间中自动工作，但玩家仍应通过走位决定覆盖、目标接近和风险承担。升级的价值不只在裸伤害，也包括范围、频率、控制、目标处理和构筑协同。

### 5.3 Combo

Combo 是把多个技能或行为关系转化为新的战斗节奏和识别点。它应让玩家看见“我的选择正在互相作用”，而不是只显示一个更大的数字。Combo 的视觉、音频和命中反馈必须能表达触发关系，同时不得重新结算伤害或成为第二套机制真源。

### 5.4 Meta 与长期记忆

未来若引入 Meta，应优先扩展决策空间，不预先锁定具体 Meta 结构。

## 6. 敌人、阶段与 Boss 的体验职责

敌人应制造不同、可读、可归因的操作题，但本 GDD 不固定敌人 taxonomy。具体分类、行为、密度和威胁结构由对应专项根据当前问题与证据决定。

阶段应采用“压力—化解—释放—再加压”的节奏。屏幕可以有大量可见敌人，但同一时刻真正要求玩家处理的高威胁行为必须有限、可读、可解释。强构筑应让玩家感到“曾经有威胁的敌人现在可以快速处理”，同时保留少量需要认真操作的目标。

Boss 的抽象职责是综合毕业考试，检验玩家对路线、闪避、构筑输出和贪婪控制的综合理解。具体机制由 Boss 专项决定。

## 7. 战斗反馈与可读性

战斗信息按“预警—行动—命中—结果”组织。玩家应能区分自己的技能、敌人的威胁、资源收益、受伤原因和阶段变化。反馈层可以使用颜色、形状、层级、震动、文字和声音，但每种媒介应有明确职责，不能靠叠加噪声代替解释。

- 预警优先表达即将发生的危险和方向。
- 命中优先表达目标、强度和成功归因。
- 成长优先表达构筑变化和力量反差。
- 高密度场景优先保留蛇头、特殊敌人和关键资源的识别度。
- 移动端与窄屏布局以可读和可操作为先，具体尺寸由现有实现和专项验收决定。

## 8. 死亡、胜利与蛇生结算

死亡应先让玩家理解发生了什么，再把注意力带入回忆和蛇生文本。战斗噪声收束、关键节点回放、局内选择和最后死法共同构成结算材料。AI 或模板化文字的实现方式属于系统与文案专项；设计目标是让结局像这条蛇独有的履历，而不是通用评价。

胜利不应抹平过程中的选择。结算可以记录击杀、构筑、危险路线、特殊事件和关键失误，让完成与失败都成为下一局的动机。结算呈现、跳过方式和文字长度由当前 UI/叙事专项决定，不在本 GDD 固定运行时参数。

## 9. AI 蛇生与记忆

本作的叙事价值来自战斗数据的二次利用：玩家吃了什么、选择了什么、如何走位、何时受伤和如何结束，组成一份可被回看的生命履历。蛇身节点可以承载战力、技能或记忆意义，但具体数据结构、存储方式和生成管线属于实现层，不由 GDD 直接锁定。

AI 蛇生的设计目标是具体、克制、可回味，并与本局事实相符。生成式内容必须有稳定降级路径；如果无法可靠生成，应优先保证结算仍可读、可重复验证，不牺牲核心战斗体验。

## 10. 视觉、音频与技术边界

- 视觉美术负责身份、材质、状态和情绪层级；程序表现负责时序、方向、命中、粒子和动态反馈。
- 音频负责事件语义、优先级、密度、生命周期和情绪转场；不得用重复播放掩盖事件归属不清。
- Canvas 与原生 JS 的多文件结构、模块边界、事件通信和资源入口属于工程契约，由 `AGENTS.md`、`docs/ARCHITECTURE.md` 与代码定义。
- 当前运行时数值唯一入口是 `snake55/02_config.js`。旧数值表、Notion 页面和历史数字只用于设计追溯，不要求 CONFIG 从旧表导出或与旧表同步。

## 11. 历史层说明

早期 MVP、纯色块原型、美术替换路线、旧多文件实现路线、旧阶段时长和旧数值表，都是设计过程中的历史记录，不代表当前项目状态或下一步计划。原始长版 GDD 仍可从 Git 历史追溯；本文件保留其核心设计 DNA，并把实现事实、运行时数值和历史实验移出当前设计层。

## 12. 设计验收问题

每次扩展玩法前，至少回答：

1. 玩家此刻想要什么，又在冒什么风险？
2. 这项内容给玩家增加了什么新的操作题或选择？
3. 强大、危险、收益和失败是否可读且可归因？
4. 它是否服务蛇身身份、贪婪张力或“爽—静”情绪闭环？
5. 它是否需要独立的真理源、实现边界和验收方式？

如果只能回答“数值更高、敌人更多或表现更炫”，则不足以证明设计成立。
